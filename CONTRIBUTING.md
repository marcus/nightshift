# Contributing to Nightshift

Thanks for helping improve Nightshift! This guide covers getting a local
build running, the commit and branch conventions the project expects, and how
to preview the documentation site.

Nightshift is a Go CLI and is also self-hosting — many contributions land as
branches and PRs generated by Nightshift's own tasks. Human and machine
contributions follow the same workflow described below.

## Prerequisites

- **Go** 1.24 or newer (see `go.mod`)
- **Git**
- **golangci-lint** (optional but recommended for `make lint`) —
  `go install github.com/golangci/golangci-lint/cmd/golangci-lint@latest`
- **Node.js** (only if you intend to preview the docs site under `website/`)

## Getting the source

```bash
git clone https://github.com/marcus/nightshift.git
cd nightshift
```

## Building and testing

The project ships a `Makefile` with the common targets:

```bash
make build          # build the nightshift binary
make test           # go test ./...
make test-verbose   # go test -v ./...
make test-race      # go test -race ./...
make coverage       # go test -coverprofile=coverage.out ./...
make coverage-html  # coverage report in HTML
make lint           # golangci-lint (requires golangci-lint installed)
make check          # test + lint
make clean          # remove build artifacts
```

`make check` is the fastest way to confirm your change is ready: it runs the
full test suite and the linter.

## Formatting and the pre-commit hook

Go code must be `gofmt`-clean and pass `go vet`. Install the git pre-commit
hook once per clone:

```bash
make install-hooks
```

This symlinks `scripts/pre-commit.sh` into `.git/hooks/pre-commit`. On every
commit it runs:

- **gofmt** — flags any staged `.go` file that needs formatting
- **go vet** — catches common correctness issues
- **go build** — ensures the project still compiles

To bypass the hook in a pinch: `git commit --no-verify` (avoid this on shared
branches).

## Branch and pull request workflow

1. **Branch from `main`.** Never commit directly to `main`.
   ```bash
   git checkout main
   git pull --ff-only
   git checkout -b <type>/<short-description>
   ```
2. Make your change, keep commits focused, and run `make check`.
3. Push your branch and open a pull request against `main`.
4. Make sure CI and the preflight checks are green before requesting review.

Branch naming mirrors the conventional-commit type, e.g.
`fix/budget-underflow`, `docs/contributing`, `feat/new-task`.

## Commit message conventions

Use [Conventional Commits](https://www.conventionalcommits.org/). The project
history uses this style throughout (for example
`fix: block task run in sensitive directories`).

```
<type>(<optional scope>): <imperative summary>

<optional body explaining why>

<optional trailers>
```

Common types:

- `feat` — a new feature
- `fix` — a bug fix
- `docs` — documentation only
- `refactor` — code restructuring with no behavior change
- `test` — adding or correcting tests
- `chore` — tooling, build, deps, CI
- `perf` — performance improvement

Keep the summary to one line in the imperative mood ("add", "fix", "remove"),
lowercase, no trailing period. Reference the issue or PR number in the body or
trailer when relevant (e.g. `Closes #14`).

### Nightshift-generated commits

Commits produced by Nightshift tasks include two trailers so they can be
traced back to the task that created them:

```
Nightshift-Task: <task-type>
Nightshift-Ref: https://github.com/marcus/nightshift
```

For example, a documentation backfill commit ends with:

```
Nightshift-Task: docs-backfill
Nightshift-Ref: https://github.com/marcus/nightshift
```

When reviewing or hand-writing commits that should be attributable to a
Nightshift task, include these trailers.

## Previewing the documentation

The documentation site is a [Docusaurus](https://docusaurus.io/) project under
`website/`. Markdown sources live in `docs/` and are surfaced through the site.

```bash
cd website
npm install
npm start          # local dev server with hot reload
npm run build      # production build into website/build/
```

Guides live in `docs/guides/`, implementation and design notes in
`docs/implemented/`. When adding a new guide, follow the structure of an
existing one (see `docs/guides/adding-tasks.md`).

## Scope

- Bug fixes and improvements to existing tasks and packages are always welcome.
- New built-in tasks go in the task registry — see
  [`docs/guides/adding-tasks.md`](docs/guides/adding-tasks.md) for the full
  walkthrough (constant, registry entry, completeness test).
- Provider integrations belong in `internal/providers/`; calibration tooling
  in `cmd/provider-calibration/`.

## Security notes for contributors

Nightshift runs AI agents that can execute code, so the security boundaries in
`internal/security/` matter. In particular:

- `security.ValidateProjectPath` refuses to operate in sensitive directories
  (`/`, `/tmp`, `/var`, `/etc`, `/usr`, and the user's home). Preserve this
  guard for any change that resolves project paths.
- Git pushes are gated by `security.ValidateGitPush` and require `--allow-push`.
- Database and credential handling defaults to restrictive permissions
  (`0700`); do not relax these without discussion.

If you find a security issue, please do not open a public PR — report it
privately to the maintainers first.
